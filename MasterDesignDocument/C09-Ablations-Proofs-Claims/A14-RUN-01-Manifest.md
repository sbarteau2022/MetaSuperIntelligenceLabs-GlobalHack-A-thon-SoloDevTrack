## 1. Resolution target (naming the gap honestly)

Prereg §A14 names the unit under test `resolve_v2`. [VERIFIED 2026-10-30 — `grep resolve_v2` over `research-grade-harness/src/*.rs`: no matches] No function literally named `resolve_v2` exists in the harness. The resolution surface that DOES exist and governs tool admission:

- `CapabilityDag::resolve_tool(&str) -> Option<&CapabilityNode>` (`research-grade-harness/src/capability.rs:302`) — 4-stage match: exact id → leaf-of-id → skill_path → leaf-of-skill_path; `None` on miss.
- `CapabilityGate::admit(&str) -> Result<&CapabilityNode, String>` (`capability.rs:356`) — `resolve_tool` + `deny_unknown` fail-explained denial on miss.
- `Engine::execute_packet_n3` calls `gate.admit(&tc.tool)` per `map.*` tool_call before transport (`engine.rs`); non-`map.*` tools take the legacy path (caller-appended, NOT gated — out of scope for this run).

**Binding decision (frozen for RUN-01):** the A14 determinism claim is tested against `CapabilityGate::admit` = the shipped admission path. `resolve_v2` (C29 spec) is the design name; `admit` is its implementation. If `admit` proves nondeterministic, the defect is filed against the SKL-06/TOOL-06 family per prereg null-handling, and a `resolve_v2`-named wrapper is NOT invented to pass the run.
