CUDA Rust, read as a substrate problem.

CUDA Rust is not one thing. It is two Rust tracks over one shared runtime — cuda-oxide for SIMT kernels and cutile-rs for tile kernels. The tile is the portable unit. The vendor boundary is not.

Two tracks, one runtime

NVIDIA's own rule: Tile first. SIMT when you need the control Tile deliberately hides.

Track 01 — TileReach for first

cutile-rs

You write what one tile block does to a sub-tensor. The host partitions a tensor; CUDA Tile IR JIT-compiles the kernel and decides thread mapping and layout per NVIDIA architecture.

  • Stable Rust 1.89+ · CUDA 13.3 recommended · Linux · no nightly, no custom LLVM
  • Published on crates.io — cargo add cutile
  • Safety by partitioning: each tile block exclusively owns its chunk; grid follows from the partition
  • Used in Hugging Face Grout and mistral.rs; cutile README also cites Candle MoE kernels
  • Examples: hello_world · saxpy · async_gemm + a cutile-kernels crate

Further along — still early-stage, not production-ready

Track 02 — SIMTEarly alpha

cuda-oxide

You write what one thread does. A custom rustc codegen backend routes #[kernel] through Rust MIR → Pliron IR → LLVM IR → PTX. Host and device code in one file.

  • Explicit thread / block / warp / cluster / TMA control, shared memory, synchronisation
  • Safety by DisjointSlice + typed thread index + #[launch_contract] validation
  • Shared memory still requires unsafe today — NVIDIA calls making it safe “active work”
  • Linux · CUDA 12.x+ · clang / libclang · GPU CC 8.0+
  • Toolchain in flux — see the disagreement flagged below

Assess, do not ship on it

Use Tile when

The problem is dense tensor math and you want the compiler to schedule it — and the strongest safety claim of the two.

Use SIMT when

Porting CUDA C++, or the work is sparse / pointer-chasing, or you need warps, shared memory, TMA or cluster ops directly.

⚠ Toolchain disagreement, reported not resolved: the NVIDIA blog (8 Sep 2026) pins nightly-2026-04-03; the current docs hub (read 27 Oct 2026) says a pinned stable Rust 1.99.1 managed by cargo oxide. Check the cuda-oxide book before scripting any setup. Shared runtime for both tracks: cuda-bindings · cuda-core · cuda-async — Tile and SIMT kernels interoperate on the same stream over shared buffers.

Same kernel, two ways

Both tracks demo the identical 1,024-float vector add — so the abstraction gap is visible in the code itself.

// Tile: no thread indices anywhere. Partitioning IS the safety argument.
#[cutile::module]
mod kernel {
    #[cutile::entry()]
    fn add<const B: i32>(
        z: &mut Tensor<f32, { [B] }>,   // exclusive output sub-tensor, B = tile width
        x: &Tensor<f32, { [-1] }>,      // shared input; -1 = dynamic dim
        y: &Tensor<f32, { [-1] }>,
    ) {
        let tx = load_tile_like(x, z);
        let ty = load_tile_like(y, z);
        z.store(tx + ty);               // elementwise across the whole tile
    }
}
// host: api::zeros::<f32>(&[1024]).partition([128])  →  8 tiles, grid follows
// cargo add cutile, then cargo run  →  PASSED: all 1024 elements correct
// SIMT: the signature IS the safety argument.
#[cuda_module]
mod kernels {
    #[kernel]
    #[launch_bounds(256)]
    #[launch_contract(domain = 1, block = (256, 1, 1))]
    pub fn vecadd(a: &[f32], b: &[f32], mut c: DisjointSlice<f32>) {
        let idx = thread::index_1d();   // typed index, not a bare usize
        if let Some(c_elem) = c.get_mut(idx) {
            *c_elem = a[idx.get()] + b[idx.get()];
        }
    }
}
// DisjointSlice splits one &mut into per-thread exclusive pieces —
// a plain &mut [f32] shared by every thread is what Rust correctly refuses.
// Aliasing c as its own input fails: error[E0502] cannot borrow as mutable…
// cargo oxide new vecadd_demo && cargo oxide doctor && cargo oxide run

Why cutile's claim is stronger: cuda-oxide checks each launch call; cutile's ownership follows the tensors across the launch boundary. Aliasing the output as an input there fails with error[E0382]: use of moved value: z. Host ops in cutile are also lazy — nothing runs until .sync_on(&stream).

The substrate map

The microkernel is the tile, not the thread. cutile-rs is one entry in a registry — not the registry itself.

1 · Microkernel spec

A small, named, testable unit — fused norm, attention tile, quantised GEMM epilogue — defined only by tensors, shapes, dtypes and tile sizes.

  • Input tiles: shared
  • Output tile: exclusive
  • Tile width: const generic
→

2 · Kernel registry

Name → signature, tile-shape parameters, capability requirements, and one implementation per substrate. No ready-made Rust standard for this was found — it is architecture you build.

  • Closest analogue: ONNX Runtime's per-provider KernelRegistry
  • Closest crate: cutile-kernels
→

3 · Dispatcher

Detect the device at runtime, select the backend, autotune per device at first run, and fail loudly on a missing kernel or capability — never silently fall back.

  • Tuning does not transfer across substrates, even when source does
NVIDIA — cutile-rs

Tile IR JIT to cubin. The design reference: kernel body contains no warp, block or tensor-core vocabulary.

NVIDIA — cuda-oxide

The escape hatch inside the same substrate, for warp reductions, TMA pipelines, clusters, sparse structures.

Apple Silicon — Metal

MSL compute kernel (or WGSL via wgpu): threadgroup = block, simdgroup = warp, threadgroup memory = shared memory, simdgroup_matrix / MPS = tensor cores.

Why this stays model-agnostic

A microkernel's contract is tensors, shapes, dtypes and tile sizes — not Qwen, Llama or Mistral. Grout is a Qwen3 engine, but its cutile kernels are generic operators (attention, fused norm, elementwise, embedding, argmax; dense projections go to cuBLAS), and mistral.rs's cutile feature covers quantised linear layers and MoE. That separation is what lets a product ship over the internet: weights travel in portable formats (safetensors, GGUF), and the binary carries a registry + runtime detection + JIT/autotune, so the machine it lands on picks the implementation that exists there.

✓ What CUDA Rust gives

  • Rust-native NVIDIA kernels with compile-time aliasing / race rejection
  • A tile-shaped unit whose body holds no hardware vocabulary — the right specification layer
  • A shared runtime and same-stream Tile ↔ SIMT interop: a working example of the registry seam
  • Real adoption signal and near-cuBLAS paper claims for the Tile track

✕ What it does not give

  • Production readiness — both tracks early-stage, APIs moving
  • Cross-vendor portability — Tile IR / PTX / cubin are NVIDIA-only
  • A Metal backend, a registry, or a dispatcher — you build those around it
  • Automatic determinism or performance portability — reduction order, TF32/MMA behaviour and per-arch tuning still need explicit design

What breaks between substrates

The honest list. Portability of source is not portability of performance — or of assumptions.

DifferenceWhat actually changes
Vendor boundaryTile IR portability means across NVIDIA architectures (sm_80–sm_121). There is no Metal target. Cross-vendor is a separate layer's job.

Could not verify

Open questions from the research pass, stated plainly rather than smoothed over.

  • Toolchain: whether pinned stable 1.99.1 (docs hub) has fully replaced the blog's pinned nightly for cuda-oxide, and what the current cargo oxide install command is. The two primary sources disagree by date.
  • Secondary-only claims: the three-tier safety model, the gemm_sol example at 868 TFLOPS on B200 (58% of cuBLAS solution), index_2d(stride) documented unsound in 0.x, and cutile 0.3.1 / deny_in_kernel_checks — none confirmed against the NVIDIA books in this pass.
  • Mac cross-compile: whether CUDA Rust host code can be cross-compiled from macOS for a remote NVIDIA target without a local GPU — no source found. Do not assume it.
  • Ready-made registry: whether any Rust crate today provides a cross-substrate microkernel registry (name → CUDA Tile + Metal + WGSL) — none found. CubeCL is the closest pattern, not a drop-in registry.
  • Named standards: “kernel registry” and “deterministic kernel” as Rust-ecosystem standards — no canonical standard found.
