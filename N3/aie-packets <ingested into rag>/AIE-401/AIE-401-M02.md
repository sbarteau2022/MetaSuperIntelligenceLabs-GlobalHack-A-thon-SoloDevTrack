## Module overview

Sprint I ships one thing: a **core loop** — the minimal, real, end-to-end path from an input
your system will actually receive to an output it will actually return — with an **eval gate**
that actually blocks a bad build, proven by actually breaking the build and watching the gate
catch it.

The exemplar is **TicketTriage**: given the text of a new support ticket, retrieve the most
similar past resolved tickets, classify the ticket's category, and draft a response citing the
retrieved resolution. Small on purpose. Every stage is hand-built from the standard library —
a from-scratch TF-IDF retrieval index, a rule-based classifier, a templated response
generator — because Sprint I's job is not to be impressive, it is to be **real and measured**.
The eval gate is an AIE-204-style harness: a held-out gold set of 12 hand-labeled tickets, three
metrics, three thresholds, one decision rule, wired into a script that exits nonzero and blocks
the build when a metric misses.

By the end of this module the exemplar's gate will have actually failed once (on a real,
planted regression) and actually passed once (on the fix) — with the literal terminal output
reproduced in Lab B, not summarized. Lab C then asks you to do the same thing to your own
project: a loop that actually runs, a gate that actually measures, and — in the module
assessment — a planted regression in *your* code that your gate either catches or doesn't.

## Lessons

### Lesson 1 — The core loop is a contract, not a feature list

**Teaching text**

Before TicketTriage has a single line of retrieval or classification code, it has this:

```python
@dataclass
class TicketResult:
    ticket_text: str
    category: str
    retrieved: list[tuple[str, float]]
    draft_response: str
    latency_ms: float
    log: dict
```

That's the whole of Lesson 1: **write the shape of the loop's input and output before you
write anything that produces them.** Every stage inside the loop — retrieval, classification,
response drafting — is free to change entirely (hand-rolled TF-IDF today, a real embedding
index tomorrow; keyword rules today, your AIE-301 fine-tuned classifier tomorrow) as long as it
keeps honoring this contract. The eval harness in Lesson 3 depends on this shape. The logging
pipeline your production system will need in M03 depends on this shape. A on-call engineer at
2am reading a log line depends on this shape existing and not silently drifting. This is the
same discipline AIE-303 taught for a served model's request/response contract, one level up:
here the "endpoint" is your whole system, and the contract has to survive the sprint that comes
after this one.

A **core loop**, for the purposes of this module, is defined as: the shortest path through
your system that a real input can take and produce a real output, with every stage that will
exist in production represented by *something* — even a stub — so the loop is genuinely
end-to-end. TicketTriage's loop is four stages: retrieve → classify → respond → log. Your
project's loop might be three stages or six. What it cannot be is a loop with a stage missing
because "we'll add eval later" — that stage is not later, it is now, and Lesson 3 is why.

**Worked example**

TicketTriage's loop, written down before any stage's internals existed:

```python
def handle_ticket(ticket_text: str, k: int = 3) -> TicketResult:
    retrieved = _INDEX.retrieve(ticket_text, k=k)      # stage 1: retrieval
    category = classify(ticket_text)                    # stage 2: classification
    draft_response = draft(ticket_text, category, retrieved)  # stage 3: response
    log = {...}                                          # stage 4: logging
    return TicketResult(...)
```

Notice what is *not* here: no model call, no framework, no error handling beyond what each
stage does internally. That is deliberate — Sprint I's core loop is the smallest thing that is
honestly end-to-end, not the smallest thing that compiles. A loop with retrieval stubbed to
`return []` would compile. It would not be a core loop, because it would not represent the
stage that Lesson 3's gate needs to measure.

**Named misconceptions**

- **"The core loop is the model call."** No — the model (or, in TicketTriage's case, the
  classifier and the response template) is one stage inside a loop that also includes
  retrieval, decision logic, and logging. A learner who ships only the model call has not
  built a core loop; they have built a demo cell in a notebook. The giveaway: if you cannot
  point to where the loop logs a structured record of what happened, you have not built the
  loop, you have built the trick.
- **"MVP means skip eval until it's real."** This module's entire design refutes this.
  TicketTriage's gate exists *before* the retrieval index is tuned, *before* the classifier's
  rules are polished, because the gate is what tells you whether tuning helped. A Sprint I
  without a gate is not a smaller version of a real build sprint — it is a different, weaker
  activity that happens to produce similar-looking code.
- **"The contract can be finalized later, once I know what the loop needs."** The contract is
  *how* you find out what the loop needs — writing `TicketResult`'s five fields down first is
  what forced the decision that logging is a first-class stage, not an afterthought bolted onto
  whichever function happened to run last.

### Lesson 2 — Building the loop from scratch: retrieval, decision, response

**Teaching text**

Sprint I's build work is three small, honest stages, each demonstrating the same descend-first
discipline the rest of this curriculum has used since AIE-102: before importing a library that
hides the mechanism, build the mechanism once.

**Retrieval**, hand-built as TF-IDF + cosine similarity — no `sklearn`, no vector database.
Term frequency counts how often a word appears in a document; inverse document frequency
down-weights words that appear in *every* document (they carry no discriminating signal);
multiplying them and normalizing to unit length turns each document into a vector where
cosine similarity between two vectors is a meaningful score of topical overlap. This is roughly
40 lines of Python and it is the same mathematical object a production embedding index
computes with a neural encoder instead of counting — the *interface* (`retrieve(query, k)` →
ranked results) is what survives the swap to a real index; the arithmetic underneath does not
have to.

**Decision**, here a rule-based classifier — keyword lists mapped to four categories, checked
in priority order. This is the module's clearest example of a **swappable surface** living
inside a **durable loop**: `classify(text) -> str` does not care whether its 30 lines are
keyword rules or a served model from your own AIE-301 work, as long as it returns one of the
contract's labels. Shipping the cheap version first is not a shortcut taken instead of doing
the work — it *is* the work, because Lesson 3's gate is what will tell you, in a number,
whether a fancier version is worth building at all.

**Response**, a template that opens with a category-specific line and cites the top retrieved
resolution verbatim. In a real system this stage is where an LLM call goes — prompted with the
retrieved context, the ticket text, and the classified category. TicketTriage's version has no
model in it at all, and that is intentional: the loop's *shape* around the generation stage is
what this lesson teaches, and that shape does not change when you swap a template for a real
API call in your own project.

**Worked example**

Run the loop, once, on a real ticket, and read the actual output:

```
>>> from tickettriage.loop import handle_ticket
>>> result = handle_ticket("I was charged twice for my subscription this month.")
>>> result.category
'billing'
>>> result.retrieved
[('T-101', 0.583), ('T-104', 0.152), ('T-102', 0.117)]
>>> result.draft_response
"Thanks for flagging this billing issue. Refunded the duplicate charge and applied a
billing hold note to your account so it will not recur."
```

T-101 in the resolved-ticket corpus is "I was charged twice for my subscription this month" —
nearly the same sentence. A cosine score of 0.583 against the runner-up's 0.152 is retrieval
working as intended: a strong, unambiguous top match. Log this number. Lesson 3 depends on
being able to compare *this specific loop's* output, not a hypothetical one, against a
held-out gold set.

**Named misconceptions**

- **"Hand-rolling TF-IDF is a waste of Sprint I's time — just import a library."** The library
  is the right call for your own capstone project (Lab C does not require you to hand-roll
  anything). The hand-roll here is pedagogical: you cannot reason about *why* a retrieval
  regression happens (Lesson 3) if you have never seen what "IDF" divides by.
  Descend once, then ascend and use the library everywhere after.
- **"A rule-based classifier isn't a real AI system, so it doesn't need to be measured like
  one."** The gate in Lesson 3 does not care what produced `category` — a keyword rule, a
  regex, a fine-tuned transformer. Every stage that changes the loop's output is in scope for
  eval. Excluding a stage from measurement because it "isn't the AI part" is exactly how a
  broken classifier ships silently.
- **"Retrieval and classification are basically the same problem."** They fail independently
  in TicketTriage's own numbers below — a ticket can be perfectly retrieved and still
  misclassified, or correctly classified with retrieval pointing at the wrong precedent. Lesson
  3's regression makes this concrete: a bug that leaves retrieval untouched can still gut the
  system's actual usefulness.

### Lesson 3 — Eval gates that actually block: the AIE-204 shape, wired into a build

**Teaching text**

An eval gate is AIE-204's five-commitment eval anatomy, aimed at a build instead of a research
question:

| Commitment | TicketTriage's answer |
|---|---|
| Task definition | Triage a new, unseen support ticket |
| Gold set | 12 hand-labeled tickets, disjoint from the 12-ticket retrieval corpus |
| Metric(s) | category accuracy · retrieval hit@3 · keyword coverage of the draft |
| Decision rule | per-metric threshold; **all three** must clear for the gate to pass |
| Statistic | point estimate + N; N=12 is stated honestly as too small for a real
confidence interval — the report says so rather than implying more precision than it has |

Three things separate a real gate from a decorative one. First, it runs against a **held-out**
gold set that is not the same data the system was built or tuned against — TicketTriage's gold
set (`G-01` … `G-12`) is a different 12 tickets than the resolved-ticket corpus (`T-101` …
`T-304`) retrieval draws from; mixing them would let the system "pass" by memorizing its own
index. Second, the decision rule is a **hard threshold with a real exit code**, not a chart a
human is supposed to remember to look at. Third — and this is the part a demo always
skips — the gate has to have **actually failed at least once** against a real regression before
you can trust that it will fail again when it matters.

Running this gate for real against the loop built in Lesson 2 produces a report shaped exactly
like the anatomy table above: a per-metric row, a threshold, a PASS/FAIL, and one overall
verdict. TicketTriage's own first real run clears all three thresholds — but not by a wide
margin on every metric, because a first-pass rule-based classifier has genuine, explainable
misses baked into it. Two shapes of miss are worth knowing before you ever run the gate
yourself: a **keyword collision**, where an earlier-priority category's keyword happens to
appear in a ticket that actually belongs to a later-priority category, so the wrong rule fires
first (checking `bug` keywords before `access` keywords means a ticket about `"my login won't
work"` could hit `bug`'s `"won't work"` before `access`'s `"login"` is ever checked); and a
**literal-phrase miss**, where a rule list matches only specific substrings and a ticket
describes the same symptom in different words (a rule list that contains only the literal
phrase `"blank screen"` will not fire on a ticket that says `"the page loads and shows
nothing"`). Both are real weaknesses of a keyword classifier, not noise, and the gate's 0.80
`category_accuracy` threshold was set with this in mind — a first-pass rule-based classifier
was never expected to hit 1.0. Lab A's Predict step asks you to find out, before you're told,
exactly which of the exemplar's gold tickets these two failure shapes catch; Lab B's Predict
step asks you to find out exactly how far short of a perfect score a real run lands. The
genuine numbers for both live in those labs' own Verify sections, run for real — not previewed
here.

Now watch the gate do its actual job on a regression. A teammate "simplifies" the response
stage — grabbing `retrieved[-1]` (the *worst* of the top-3 matches) instead of `retrieved[0]`
(the best), an off-by-index refactor that reads as harmless in a diff. Two of the gate's three
metrics do not move at all: the classifier never saw the change, and the right past ticket is
still sitting in the top 3 either way, so a retrieval-quality check run in isolation would
report this build as flawless. Only `keyword_coverage`, measured on the loop's actual final
output, catches it — because the bug lives in the stage that turns a correctly-retrieved match
into an actually-useful response, and that stage is exactly what `keyword_coverage` scores.
This is the single most important fact this lesson teaches: **per-stage metrics are necessary
but not sufficient; the gate must also score the loop's real, end-to-end output**, because a
bug can leave every intermediate stage's number perfect while destroying the thing a user
actually receives. Lab B's Verify section runs this exact regression for real and shows you the
literal terminal output, failing cases and all — not a summary of it.

**Worked example**

The fix for this class of bug is always the same shape: restore the correct index (or
variable, or rule) and the gate returns to producing the exact same passing numbers it produced
before the regression — byte for byte, run after run. That reproducibility (same code, same
gold set, same numbers, every time) is what makes a gate trustworthy enough to block a merge
on. A gate whose numbers drift run to run without a code change is not measuring the build; it
is measuring noise, and Lab B's Verify step checks for exactly this, on the exemplar's own real
fail-then-pass cycle.

**Named misconceptions**

- **"If the unit tests pass, the gate is redundant."** TicketTriage's unit tests (Lesson 2's
  `test_loop.py`) check that each stage does what it claims in isolation — tokenization,
  ranking order, contract shape. Every one of those tests still passes after the
  `retrieved[-1]` regression, because no individual stage is "wrong" by its own contract; the
  *composition* is wrong. Only the gate, scored against ground truth, catches a composition
  bug. Keep both. They catch different failures.
- **"A perfect intermediate metric means the stage downstream is fine."** Directly disproven by
  the regression above: `retrieval_hit_at_3` held perfectly steady through a bug that made the
  system's actual output almost useless, because the bug never touched retrieval at all — only
  the stage after it. Never let a strong per-stage number stand in for measuring the loop's real
  output. (Lab B's Verify shows you exactly how steady, and exactly how useless, in real
  numbers.)
- **"The safest threshold is 1.0 — never ship anything less than perfect."** A 1.0 threshold on
  a 12-example gold set means one unlucky paraphrase blocks every future build forever,
  regardless of whether that build fixed the actual problem it was meant to fix. It is not
  rigor, it is a gate that has quietly stopped being a gate and become a wall. (The inverse —
  a threshold of 0.0, which always passes — is the same failure from the other side, and
  `tests/test_gate.py::test_gate_thresholds_are_below_perfect` exists specifically to catch a
  future engineer "fixing" a failing gate by loosening it to nothing.)

### Lesson 4 — From exemplar to your own project: the sprint checklist

**Teaching text**

Everything above was TicketTriage's. Nothing above ships in your capstone. What ships is the
**structure**: a loop contract you write down before you fill it in, and a gate you can run,
break, and fix, with real numbers each time. This lesson hands you the checklist you will fill
out for your own project in Lab C and defend in the module assessment.

**The sprint checklist — four gate criteria, each pass/fail:**

1. **The loop contract is written down and every real stage is present.** Not "the model call
   works" — every stage that will exist when this system has users, even if a stage is
   currently a stub. Evidence: the contract (a dataclass, a TypedDict, a schema — your choice)
   plus one real, logged run through the whole loop.
2. **A gold set exists, is held out from whatever the system was built or tuned against, and
   has enough examples that one lucky or unlucky case can't flip the verdict by itself.**
   Evidence: the gold set file, plus a one-line justification of *why* these examples and not
   others — what failure modes they were chosen to catch.
3. **The gate computes real metrics against real gold-set data, applies a real threshold, and
   exits with a real pass/fail — proven by making it fail once on purpose and pass once after a
   fix, exactly like Lesson 3.** A gate that has never failed has never been tested as a gate.
4. **Every threshold is justified against a cost, not set to whatever the first build already
   achieves.** Write one sentence per metric: what does it cost someone if this metric is
   lower than the threshold? A threshold with no answer to that question is not a decision
   rule, it is a rubber stamp.

Criterion 4 is where most gates quietly fail without anyone noticing, and it is why this
module's assessment (below) checks it directly rather than trusting a learner's self-report.

**Worked example**

Applying the checklist to TicketTriage itself, honestly, including where it is weakest:

| Criterion | TicketTriage | Evidence |
|---|---|---|
| 1. Loop contract + all stages present | PASS | `TicketResult`, Lesson 1; `handle_ticket`, Lesson 2 |
| 2. Held-out gold set, non-trivial size | PASS (marginal — N=12) | `GOLD_SET` disjoint from `RESOLVED_TICKETS`; harness reports N and does not claim a CI it can't support |
| 3. Gate fails-then-passes, provably | PASS | Lab B's Verify section (two literal terminal transcripts) |
| 4. Thresholds justified by cost, not by fit | PASS | 0.80 / 0.90 / 0.75 set from the *known* weaknesses of a first-pass rule classifier before the gate was ever run — not adjusted afterward to match whatever the first real run happened to score (see Lab B's Verify for the actual figures and how close the run came to each threshold) |

**Named misconceptions**

- **"Applying the checklist means copying TicketTriage's code."** No — TicketTriage's TF-IDF
  index, keyword rules, and templates are domain-specific to a support-ticket system. Your
  project's loop stages, gold set, and thresholds will look nothing like these. What transfers
  is the *shape*: contract-first, gate-before-polish, fail-then-pass proof, cost-justified
  thresholds.
- **"My project doesn't have a clean gold set yet, so I'll skip the checklist until it does."**
  The checklist does not require a large or perfect gold set — TicketTriage's is 12 examples
  and says so honestly. It requires a *real, held-out, non-trivial* one. A gold set of 8
  carefully chosen examples that actually held out from tuning beats a gold set of 200 examples
  scraped from the same data the system was built against.
- **"I'll set thresholds after I see what my first build scores, so the numbers feel fair."**
  This is threshold-gaming with a friendlier name, and it is the exact failure Lesson 3's
  `test_gate_thresholds_are_below_perfect` and this module's assessment are built to catch.
  Predict your threshold — and your reason for it — before your first gate run, per Lab B and
  Lab C's Predict steps.

**Solution** (reference — TF-IDF core, the piece most learners get stuck on):

```python
    def _idf(self, term: str) -> float:
        df = self._df.get(term, 0)
        return math.log((1 + self._n_docs) / (1 + df)) + 1.0

    def _vectorize(self, tokens: list[str]) -> dict[str, float]:
        tf = Counter(tokens)
        vec = {term: count * self._idf(term) for term, count in tf.items()}
        norm = math.sqrt(sum(w * w for w in vec.values())) or 1.0
        return {term: w / norm for term, w in vec.items()}

    @staticmethod
    def _cosine(a: dict[str, float], b: dict[str, float]) -> float:
        if len(a) > len(b):
            a, b = b, a
        return sum(w * b.get(term, 0.0) for term, w in a.items())

    def retrieve(self, query: str, k: int = 3) -> list[tuple[str, float]]:
        q_vec = self._vectorize(tokenize(query))
        scored = [(doc_id, self._cosine(q_vec, dv)) for doc_id, dv in self._doc_vectors.items()]
        scored.sort(key=lambda pair: pair[1], reverse=True)
        return scored[:k]
```

```python
# tickettriage/loop.py -- SOLUTION
def handle_ticket(ticket_text: str, k: int = 3) -> TicketResult:
    start = perf_counter()

    retrieved = _INDEX.retrieve(ticket_text, k=k)
    category = classify(ticket_text)
    draft_response = draft(ticket_text, category, retrieved)

    elapsed_ms = (perf_counter() - start) * 1000.0

    log = {
        "ticket_text": ticket_text,
        "category": category,
        "retrieved_ids": [doc_id for doc_id, _score in retrieved],
        "latency_ms": round(elapsed_ms, 3),
    }

    return TicketResult(
        ticket_text=ticket_text,
        category=category,
        retrieved=retrieved,
        draft_response=draft_response,
        latency_ms=elapsed_ms,
        log=log,
    )
```

**Solution** (`score_example` and `run_gate` — the aggregation logic):

```python
def score_example(example: GoldExample, k: int = 3) -> ExampleScore:
    result = handle_ticket(example.text, k=k)
    category_correct = result.category == example.expected_category
    retrieved_ids = {doc_id for doc_id, _score in result.retrieved}
    retrieval_hit = bool(retrieved_ids & set(example.relevant_resolved_ids))
    response_lower = result.draft_response.lower()
    keyword_hits = sum(1 for kw in example.required_keywords if kw.lower() in response_lower)
    return ExampleScore(
        example=example, result=result,
        category_correct=category_correct, retrieval_hit=retrieval_hit,
        keyword_hits=keyword_hits, keyword_total=len(example.required_keywords),
    )

def run_gate(gold_set=None, k: int = 3) -> GateReport:
    examples = gold_set if gold_set is not None else GOLD_SET
    scores = [score_example(ex, k=k) for ex in examples]
    n = len(scores)
    metrics = {
        "category_accuracy": sum(s.category_correct for s in scores) / n,
        "retrieval_hit_at_3": sum(s.retrieval_hit for s in scores) / n,
        "keyword_coverage": sum(s.keyword_coverage for s in scores) / n,
    }
    return GateReport(scores=scores, metrics=metrics, thresholds=GATE_THRESHOLDS)
```

```python
# tickettriage/eval_harness.py -- SOLUTION (added to the GateReport class above)
    def render(self) -> str:
        lines = [f"TicketTriage eval gate -- N={self.n} gold examples", ""]
        header = f"{'metric':<22}{'value':>8}{'threshold':>12}{'result':>10}"
        lines.append(header)
        lines.append("-" * len(header))
        for metric in self.thresholds:
            value = self.metrics[metric]
            threshold = self.thresholds[metric]
            result = "PASS" if self.passed(metric) else "FAIL"
            lines.append(f"{metric:<22}{value:>8.3f}{threshold:>12.3f}{result:>10}")
        lines.append("")
        lines.append(f"GATE: {'PASS' if self.all_passed else 'FAIL'}")
        return "\n".join(lines)
```

```python
# tickettriage/eval_gate.py -- SOLUTION
from __future__ import annotations
import sys
from .eval_harness import ExampleScore, run_gate

def main() -> int:
    report = run_gate()
    print(report.render())

    if report.all_passed:
        return 0

    print()
    print("Gate FAILED -- blocking build. Failing examples:")
    for metric in report.thresholds:
        if report.passed(metric):
            continue
        failing = [s for s in report.scores if _example_fails(s, metric)]
        print(f"  metric '{metric}' below threshold; failing cases:")
        for score in failing[:2]:
            print(f"    {score.example.example_id}: {_failure_detail(score, metric)}")
        if len(failing) > 2:
            print(f"    ... ({len(failing) - 2} more)")
    return 1

def _example_fails(score: ExampleScore, metric: str) -> bool:
    if metric == "category_accuracy":
        return not score.category_correct
    if metric == "retrieval_hit_at_3":
        return not score.retrieval_hit
    if metric == "keyword_coverage":
        return score.keyword_coverage < 1.0
    return False

def _failure_detail(score: ExampleScore, metric: str) -> str:
    example = score.example
    if metric == "category_accuracy":
        return f"expected '{example.expected_category}', got '{score.result.category}'"
    if metric == "retrieval_hit_at_3":
        return f"no relevant resolved ticket in top-k (expected one of {tuple(example.relevant_resolved_ids)})"
    if metric == "keyword_coverage":
        response_lower = score.result.draft_response.lower()
        missing = tuple(kw for kw in example.required_keywords if kw.lower() not in response_lower)
        return f"missing keywords in draft -- {missing}"
    return "failed"

if __name__ == "__main__":
    sys.exit(main())
```

about a failing case (a category mismatch, a missing retrieval hit, a missing keyword) is

## Assessment

Maps to AIE-401's "shipped system" and "artifact set" components. Gaming-resistance is the
design constraint: a learner cannot pass this module by describing a loop and a gate — only by
running one, breaking it, and fixing it, with a reviewer able to reproduce every claimed number.

**The certification check.** After Lab C is submitted, a reviewer applies **one unseen,
planted regression** to the learner's own core loop — not one the learner chose or has seen —
and runs the learner's own gate against it, exactly as AIE-102's exam handed learners an unseen
mutated C program. The learner then has one attempt to (a) predict, from the gate's failing
metric alone, which stage the regression most likely lives in, (b) locate it by reading their
own code, (c) fix it, and (d) prove the fix by re-running their own gate to a clean pass. A gate
that does not exist, that always passes regardless of the regression, or whose thresholds were
tuned after the fact to whatever the learner's build already scored, fails this check
immediately, regardless of how polished the rest of the submission is — this is the module's
hard gate on Lesson 4's Criterion 3 and 4.

| Dimension | Fails | Meets | Exceeds |
|---|---|---|---|
| **Loop contract & completeness** | A stage is missing, stubbed with no logging, or the loop only runs on hand-picked happy-path input | Every real stage present, contract documented, one full real run logged | Contract anticipates a stage the learner hasn't built yet (e.g., a monitoring hook) with a documented reason it's deferred to M03, not forgotten |
| **Gate exists and actually runs** | No gate, or a gate that computes nothing real (hard-coded numbers, "eyeballed" pass/fail) | Gate computes real metrics against a real, held-out gold set, exits nonzero on failure | Gate is wired into an actual pre-commit or CI hook, not just runnable by hand |
| **Gate has proven fail-then-pass** | Never shown failing, or "failing" demonstrated only in prose | Learner's own submitted transcript shows a real FAIL with real numbers, then a real PASS after a real fix | The proof regression is realistic (the kind a teammate could introduce), not a toy designed to trivially fail |
| **Predict artifacts** | Missing, or written after the Build step (detectable: predictions that suspiciously match the actual result to the decimal, or that hedge every direction) | Present before each Build, falsifiable, and scored on reasoning quality independent of whether the prediction was numerically exact | Predictions name a specific mechanism (a keyword rule, an index property) rather than a vague hunch, and the falsification criterion in Lab C is genuinely falsifiable |
| **Thresholds cost-justified** | Thresholds match whatever the first build scored, or have no stated justification | Each threshold has a one-sentence cost-of-being-wrong justification written before the first gate run | Justification is tied to a concrete stakeholder or downstream consequence, not a generic "quality bar" |
| **Certification check (unseen regression)** | Gate misses the planted regression, or doesn't exist, or the learner cannot locate/fix it from the gate's own output | Gate catches the regression; learner correctly predicts the affected stage from the failing metric, locates, fixes, and re-passes | Learner's write-up explains *why* that regression maps to that metric and not another — the same reasoning Lesson 3 modeled |

A submission can have beautiful code and still fail this module if the certification check's
gate is silent on the planted regression — that silence is the failure this whole module exists
to prevent, and it is graded as such, at full weight, no partial credit for polish elsewhere.
