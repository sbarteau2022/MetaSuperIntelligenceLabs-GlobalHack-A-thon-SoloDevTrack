## Lessons

### Lesson 1 — Quantization is bit-level arithmetic, not a checkbox

**Teaching text.** A `float32` weight is 4 bytes: 1 sign bit, 8 exponent bits, 23 mantissa bits, giving roughly 7 decimal digits of precision across an enormous dynamic range. Almost none of that range is used by a trained weight matrix — weights cluster tightly around zero, and the values you actually need to distinguish live in a narrow band. Quantization is the decision to spend fewer bits on that band on purpose.

The scheme this lesson builds is **symmetric linear (affine) quantization**, the same scheme `bitsandbytes`, `torch.quantization`, and GGUF's basic quant types all specialize from. For a weight tensor $W$ and a target signed integer width of $n$ bits (range $-(2^{n-1}-1)$ to $2^{n-1}-1$, kept symmetric so zero maps to zero exactly):

```
scale = max(|W|) / (2^(n-1) - 1)
code_i = round(W_i / scale), clipped to the integer range
W_dequant_i = code_i * scale
```

For int8, the range is −127..127 (127 codes each side, zero shared). For int4, it's −7..7 — you only get 15 usable codes total, which is why int4 error is not "a bit worse than int8," it is categorically worse: you've gone from ~1% of the dynamic range per code to ~7% of it.

**Worked example.** Take the weight row `[0.73, -0.41, 0.05, -1.02, 0.88, -0.03, 0.61, -0.97]` (a plausible slice of a real linear layer's row). `max(|W|) = 1.02`.

int8: `scale = 1.02 / 127 = 0.0080315`. `0.73 → round(0.73/0.0080315) = 91 → dequant 0.73087`. Every value round-trips within ~0.003 absolute error; the noisiest case (`0.88 → 0.88346`) is 0.4% relative error.

int4: `scale = 1.02 / 7 = 0.145714`. The same `0.73 → round(0.73/0.145714) = 5 → dequant 0.72857` looks fine, but `0.05 → round(0.05/0.145714) = 0 → dequant 0.0` — the value vanishes. `0.61 → code 4 → dequant 0.58286`, a 4.5% relative error versus int8's 0.06% on the same input. Call this the **small-weight vanishing effect**: because `scale` is set by the tensor's single largest magnitude, a coarser (fewer-bit) grid rounds every value smaller than roughly half a step to zero or to a code far off from its true value, and it does this disproportionately to small-magnitude weights — that's the arithmetic behind "int4 hurts more on layers with high weight variance," not a rule of thumb. The effect isn't specific to this one worked tensor; it applies to any tensor you point a coarse bit-width at.

Bit packing makes the storage claim real, not aspirational: two int4 codes fit in one `uint8` via `(hi << 4) | lo`, each code kept in two's-complement nibble form (`code & 0xF` to pack, `n - 16 if n >= 8 else n` to unpack a nibble back to signed). Eight int4 values pack into 4 bytes — an 8× reduction from float32's 32 bytes for the same 8 values, and 2× tighter than int8's 8 bytes. Lab M02-A implements exactly this pack/unpack pair and round-trips it before it's allowed to touch a real model.

**Named misconceptions**

- *"Quantization just truncates the number."* No — truncation (dropping mantissa bits) is a different, cruder operation on the float encoding itself. Symmetric linear quantization re-maps the whole tensor onto a new fixed-point grid sized by that tensor's own `max(|W|)`. The scale factor is why quantization is *data-dependent*: the same bit-width produces different error on a peaked-near-zero weight matrix versus a spread-out one.
- *"int4 is 'int8 but half the bits,' so expect roughly half the accuracy loss, or roughly double."* The relationship is not linear. Going from 8 bits to 4 bits does not halve your usable codes (127→63), it goes from 127 codes to 7. Error scales with the size of one quantization step (`scale`), and `scale` for int4 is roughly 18× coarser than int8's on the same tensor in the worked example above (`0.1457 / 0.00803 ≈ 18.1`).
- *"Quantizing weights and quantizing activations are the same problem."* They are not solved by the same calibration. Weights are static — you compute `scale` once, offline, from the trained tensor. Activations vary per input; a static scale computed from one calibration batch can clip badly on an out-of-distribution input. This module quantizes weights by hand (Lab M02-A) and treats activation quantization as the harder problem `torch.quantization.quantize_dynamic` is solving for you when you re-ascend to it in the same lab.

### Lesson 2 — Predicting accuracy cost before you measure it

**Teaching text.** "It got faster" is not evidence a quantization scheme is acceptable — a model that always outputs the empty string is also fast. The discipline this module insists on, per AI-PRIMM, is a written prediction of the accuracy *cost*, on paper, before the eval runs. That prediction needs a number to be checked against, so this lesson gives you the two numbers that matter: **perplexity delta** on a held-out text sample, and **task accuracy delta** on a small labeled eval (reusing an AIE-204-style harness). Speed without a measured accuracy number attached is not a result in this course — it is half a result, and labs will not accept it as a submission.

The prediction itself should be reasoned, not guessed: use the worked-example error rates from Lesson 1 (int8: sub-1% relative error on typical weights; int4: 4–7%+ relative error concentrated on small-magnitude weights) plus which layers you're quantizing (embedding and final projection layers are more perplexity-sensitive than middle-layer MLPs, because errors there act directly on logits) to predict a *direction and rough magnitude*. As an illustration of the reasoning shape — not a number to reuse — consider quantizing **only the token-embedding table** (leaving every attention/MLP layer at fp32): int8 there barely moves perplexity, because most rows sit far enough from zero that int8's ~1%-of-range step is nearly invisible; int4 there costs more, and costs it unevenly, because embedding rows for rare tokens tend to cluster nearer zero and take int4's coarser, ~7%-of-range step harder than common-token rows do. That "the error concentrates on values already close to zero" mechanism is Lesson 1's, and it transfers to *whatever* tensor you point a bit-width at — including the linear layers Lab M02-A actually asks you to quantize — but the specific direction and magnitude for that case is exactly what your own Predict step there has to work out, from this same arithmetic, not recall from here.

**Worked example.** Perplexity is `exp(average negative log-likelihood per token)`. The arithmetic below is the template you need — NLL delta → `exp()` → relative-percent — not a preview of what int8-vs-int4 on linear layers will produce, so it's put on a **different scenario** than Lab M02-A's: quantizing *only* the embedding table (the case sketched qualitatively above) to int8 versus to a much coarser int2, a bit-width pair this module's own labs never touch. If a baseline fp32 model scores an average NLL of 3.40 nats/token on a 2,000-token held-out sample, its perplexity is `exp(3.40) ≈ 29.96`. Quantizing only the embedding table to int8 nudges average NLL to 3.46 nats/token — perplexity becomes `exp(3.46) ≈ 31.82`, a 6.2% relative increase. Quantizing only the embedding table to int2 pushes average NLL to 3.95 nats/token — perplexity becomes `exp(3.95) ≈ 51.94`, a 73% relative increase. Notice what the arithmetic does, not what number it lands on: a small NLL gap (0.06 nats) and a large one (0.55 nats) turn into very different relative-percent figures once you exponentiate, which is the whole reason "report the relative change, not the raw perplexity gap" (below) matters. Redo this same NLL→perplexity→relative-percent arithmetic on *your own* measured numbers for Lab M02-A's actual case (int8 vs. int4, on linear layers, on `distilgpt2`) — the size of that delta is exactly what your Predict item there has to reason out from Lesson 1's scale-arithmetic first, not read off this embedding-table illustration.

**Named misconceptions**

- *"A 2-point perplexity increase is small."* Perplexity is exponential in NLL — a fixed additive NLL gap compounds into a larger relative perplexity gap as the baseline perplexity grows. Always report the **relative** change (or the NLL delta directly), never a bare perplexity difference; "perplexity went up by 2" means something completely different at baseline 10 than at baseline 40.
- *"One held-out sample is enough to trust the number."* A 2,000-token sample from one document has high variance; the module's Lab M02-A requires averaging over multiple non-overlapping samples and reporting a spread, not a single point estimate — otherwise a learner can cherry-pick a favorable sample without knowing it.
- *"Perplexity is the whole story."* Perplexity measures next-token prediction quality on natural text; it does not directly measure the task your system actually performs (e.g., the AIE-302 system's retrieval-grounded answer quality). A quantization level can look fine on perplexity and still degrade a specific downstream behavior a perplexity average smooths over. That is exactly why AIE-204's eval harness — not just perplexity — is the real deployment gate in M03.

### Lesson 3 — The KV cache: why generation gets expensive with length, in bytes

**Teaching text.** Self-attention's per-layer compute cost, for a sequence of length `seq_len`, is `O(seq_len²)` whenever it is computed by scoring every position against every other position in one pass — that's the formula, full stop, independent of whether or how anything gets cached. The **KV cache** changes what has to be recomputed at each new decoding step, not the formula itself: after each forward pass, it stores every layer's key and value projections for every token generated so far, and the next decoding step's self-attention draws on those stored keys/values for the *one new* query token, rather than reconstructing keys and values for the whole prefix from scratch again. That's a genuine compute/memory trade — caching spends memory that grows with sequence length (a real, budgetable number, not an abstraction, and the thing this lesson measures precisely below) in exchange for changing how much attention work each new generated token costs. What that change actually does to the compute-complexity class of decoding — for the cached case and for the uncached case, separately — is arithmetic you apply yourself, from this formula and this mechanism, in Lab M02-B's Predict step; it is not stated here.

The formula, per token, across the whole model:

```
bytes_per_token = 2 (K and V) × n_layers × n_heads × head_dim × dtype_bytes
```

For a 12-layer, 16-head, 64-dim illustrative config (hidden size 1,024 — deliberately **not** the shape of any real model this module's labs touch, so nothing in this table can be copied as an answer to a later Predict step) at fp32 (4 bytes): `2 × 12 × 16 × 64 × 4 = 98,304 bytes/token` — **96 KB per token**, before you've generated a single word of output, just to hold the cache. At fp16 that halves to 49,152 bytes/token (48 KB/token).

**Worked example.** Using the 98,304-bytes/token figure above:

| seq_len | KV cache, fp32 | KV cache, fp16 |
|---|---|---|
| 128 | 12.58 MB | 6.29 MB |
| 512 | 50.33 MB | 25.17 MB |
| 1,024 | 100.66 MB | 50.33 MB |
| 2,048 | 201.33 MB | 100.66 MB |
| 4,096 | 402.65 MB | 201.33 MB |
| 8,192 | 805.31 MB | 402.65 MB |

Now add batch: 32 concurrent requests at 2,048 tokens each, fp16, is `32 × 100.66 MB ≈ 3.22 GB` of cache *alone*, separate from the model weights themselves. This is the number that determines your maximum concurrent batch size on a fixed-memory box, and it is why "just increase the batch size" is a memory-budget decision, not a free lever — it is the direct ancestor of the $/request number this course grades throughout: more concurrent requests per GPU-second lowers cost per request, until the KV cache budget runs out and you have to queue, at which point latency (and effective cost per request, once you count idle-wait) goes back up.

**Named misconceptions**

- *"The KV cache saves memory."* It costs memory in exchange for saving *compute*. Without a cache you'd need to recompute K/V for the whole prefix at every step, which is far more FLOPs but zero extra persistent memory. The cache is a compute-memory trade, and production systems make it because compute (and the wall-clock latency it costs) is usually the binding constraint on a request's user-visible cost — but memory is what caps how many requests you can serve *at once*.
- *"KV cache size depends on how many tokens you generate."* It depends on the full sequence length seen so far — prompt tokens **and** generated tokens both sit in the cache. A long prompt with a short generation can cost as much cache as a short prompt with a long generation.
- *"Quantizing the KV cache is the same problem as quantizing weights."* Weight quantization is computed once, offline, from a static tensor. KV-cache values are produced fresh on every request from live activations — quantizing them (a real production technique, e.g. int8 KV cache) requires either a fixed calibrated scale (risking clipping on unusual inputs, same failure mode as activation quantization from Lesson 1) or per-token dynamic scales (more bookkeeping, more compute). Lab M02-B measures the unquantized cache first because you cannot reason about that trade-off until you know the baseline number in bytes.

### Lesson 4 — Speculative decoding: a small model's guesses, verified for free

**Teaching text.** Autoregressive decoding generates one token per forward pass through the full target model — every token you emit costs one full-model forward pass, even the easy, predictable ones ("the," "of," continuing a quoted string). Speculative decoding (Leviathan et al. 2023; Chen et al. 2023) exploits the fact that a much cheaper **draft model** can often guess the next few tokens correctly, and — critically — the **target model can verify a whole block of guesses in a single forward pass**, because verification is parallel (checking probabilities at positions 1..k simultaneously) while generation is sequential.

The loop, per round:

1. **Draft**: run the small draft model autoregressively for `γ` (gamma) steps, producing `γ` candidate tokens and their draft-model probabilities.
2. **Verify**: run the target model *once*, in parallel, over the draft's `γ` proposed positions (plus the position after), producing the target model's true probabilities at each position.
3. **Accept/reject**: walk the candidates left to right. Accept candidate token `i` with probability `min(1, p_target(i) / p_draft(i))` (this is the acceptance rule that makes the *combined* output distribution exactly match the target model alone — speculative decoding is a lossless sampling technique, not an approximation). At the first rejection, resample a corrected token from the target model's distribution at that position and discard the rest of the draft block.
4. If **all** `γ` candidates were accepted, the target's one extra "bonus" logit (from the position after the last draft token, already computed in the same verify pass) is sampled as a free extra token.

The expected number of tokens accepted per round, for a per-token acceptance probability `α` and draft length `γ`, is:

```
E[tokens/round] = (1 − α^(γ+1)) / (1 − α)
```

and if the draft model costs a fraction `c_draft` of a target forward pass, the expected speedup versus naive one-token-per-target-call decoding is `E[tokens/round] / (γ·c_draft + 1)`.

**Worked example.** With `γ=4` draft tokens per round, draft cost `c_draft=0.1` of the target (plausible whenever the draft model is architecturally much smaller than its target — the actual ratio for any specific pair is something you compute from that pair's own parameter or layer counts, not a number to reuse for a different pair), and acceptance rate `α=0.7` (typical for a draft model that was **trained to imitate** its target on similar data — `c_draft` and `α` are both pair-specific quantities that depend on how closely the draft's output distribution actually matches the target's; a pair with a different training relationship needs its own separate reasoning from the accept-rule mechanics, not this number reused):

`E[tokens/round] = (1 − 0.7⁵) / (1 − 0.7) = (1 − 0.16807) / 0.3 = 2.773`
`cost/round = 4 × 0.1 + 1 = 1.4`
`speedup = 2.773 / 1.4 ≈ 1.98×`

The table below is the prediction surface Lab M02-C's Predict step draws from:

| γ | α=0.5 | α=0.7 | α=0.9 |
|---|---|---|---|
| 2 | 1.46× | 1.82× | 2.26× |
| 4 | 1.38× | 1.98× | 2.93× |
| 6 | 1.24× | 1.91× | 3.26× |

Note the shape: at low acceptance (0.5), *longer* draft blocks (γ=6) are worse than shorter ones (γ=2) — you pay for more draft tokens that mostly get rejected and thrown away. Speculative decoding only pays off when the draft model is genuinely aligned with the target; a bad draft model can make generation *slower*, not faster. This is the trap the lab's Predict step is designed to catch before the learner runs anything.

**Named misconceptions**

- *"Speculative decoding is an approximation — it trades accuracy for speed."* It is not, by construction. The rejection-sampling accept/resample rule in step 3 is specifically designed so the marginal distribution of the accepted-or-resampled output token is **identical** to sampling from the target model alone. It's a wall-clock optimization with a mathematical losslessness proof, not a quality trade — which is exactly why it belongs in a production path where the target model's outputs are already gated by an eval harness (M03) that assumes target-model-quality outputs.
- *"More draft tokens per round is always faster."* As the worked table shows, γ and α interact — a longer speculation window amplifies the cost of a low acceptance rate. The optimal γ depends on measuring α for your specific draft/target pair, not picking a number from a paper trained on a different pair.
- *"The draft model needs to be a quantized copy of the target model."* It doesn't need to be related at all beyond having a compatible tokenizer — a distinct small model is a valid draft too, and is what Lab M02-C uses, specifically to explore what a draft with no shared training history with its target does to this space (that lab's own Predict step is where you reason about what a distinct, non-imitating draft does to acceptance rate — not here). A quantized copy of the target is one *option* (and often a good one, since it's cheap to produce and stays aligned with the target by construction), not a requirement of the technique.

```python
import torch
from transformers.pytorch_utils import Conv1D
# GPT-2-family models (distilgpt2 included) store their attention/MLP
# projections as Conv1D, not nn.Linear -- a holdover from GPT-2's original
# checkpoint format. Matching only nn.Linear catches lm_head (tied to the
# token embedding) and nothing else: 24 Conv1D modules per distilgpt2-shaped
# 6-layer model, carrying the weights that actually dominate the forward
# pass, would otherwise stay untouched by both the fake-quant pass below
# and the quantize_dynamic call in Part 2.

def quantize_tensor(w: torch.Tensor, n_bits: int):
    qmax = 2 ** (n_bits - 1) - 1
    maxabs = w.abs().max().item()
    scale = maxabs / qmax if maxabs > 0 else 1.0
    codes = (w / scale).round().clamp(-qmax, qmax).to(torch.int8)
    return codes, scale

def dequantize_tensor(codes: torch.Tensor, scale: float) -> torch.Tensor:
    return codes.float() * scale

def pack_int4(codes: torch.Tensor) -> torch.Tensor:
    assert codes.numel() % 2 == 0
    lo = codes[0::2].to(torch.int32) & 0xF
    hi = codes[1::2].to(torch.int32) & 0xF
    packed = (hi << 4) | lo
    return packed.to(torch.uint8)

def unpack_int4(packed: torch.Tensor) -> torch.Tensor:
    p = packed.to(torch.int32)
    lo = p & 0xF
    hi = (p >> 4) & 0xF
    def to_signed(nibble):
        return torch.where(nibble >= 8, nibble - 16, nibble)
    lo_s, hi_s = to_signed(lo), to_signed(hi)
    out = torch.empty(packed.numel() * 2, dtype=torch.int8)
    out[0::2] = lo_s.to(torch.int8)
    out[1::2] = hi_s.to(torch.int8)
    return out


def fake_quantize_module_(module: torch.nn.Module, n_bits: int):
    """Apply quantize-then-dequantize IN PLACE to every nn.Linear AND
    Conv1D weight in `module`, simulating the accuracy effect of n_bits
    storage while keeping compute in float (this is what Part 1's eval
    measures — the *accuracy* cost, isolated from any speed change).
    Conv1D's weight is stored transposed relative to nn.Linear
    ((in_features, out_features) instead of (out_features, in_features)),
    but quantize_tensor/dequantize_tensor operate elementwise on
    max(|W|), so the transpose doesn't change the quantization math —
    only the isinstance check needs to know about the type."""
    with torch.no_grad():
        for m in module.modules():
            if isinstance(m, (torch.nn.Linear, Conv1D)):
                codes, scale = quantize_tensor(m.weight.data, n_bits)
                m.weight.data.copy_(dequantize_tensor(codes, scale))


def convert_conv1d_to_linear_(module: torch.nn.Module) -> None:
    """Replace every Conv1D submodule of `module` with a weight/bias-
    equivalent nn.Linear, IN PLACE. Conv1D computes `x @ weight + bias`
    with weight shaped (in_features, out_features); nn.Linear computes
    `x @ weight.T + bias` with weight shaped (out_features, in_features)
    -- so the conversion is an exact transpose, not an approximation
    (verified: max abs logit difference on a full forward pass, before
    vs. after conversion, is numerically negligible -- ~1e-6, ordinary
    float32 matmul-order noise, not evidence of a real discrepancy).

    This step exists because torch's dynamic quantization has no
    registered swap for Conv1D: passing Conv1D in quantize_dynamic's
    qconfig_spec set does NOT error, but it is silently a no-op, because
    torch.ao.quantization.quantization_mappings
    .get_default_dynamic_quant_module_mappings() only lists nn.Linear,
    nn.LSTM, nn.GRU, and a handful of RNN cells -- Conv1D isn't in the
    registry quantize_dynamic consults, so nothing about a Conv1D module
    changes even if its type is named in qconfig_spec (checked directly
    against that mapping; a distilgpt2-shaped model still shows all 24
    Conv1D modules unconverted after such a call). Converting to nn.Linear
    first, then calling quantize_dynamic with {torch.nn.Linear}, is what
    actually makes int8 dynamic quantization reach GPT-2's attention/MLP
    weights."""
    for name, child in list(module.named_children()):
        if isinstance(child, Conv1D):
            out_features, in_features = child.weight.shape[1], child.weight.shape[0]
            linear = torch.nn.Linear(in_features, out_features, bias=child.bias is not None)
            with torch.no_grad():
                linear.weight.copy_(child.weight.t())
                if child.bias is not None:
                    linear.bias.copy_(child.bias)
            setattr(module, name, linear)
        else:
            convert_conv1d_to_linear_(child)


def perplexity(model, tokenizer, texts: list[str], device="cpu") -> float:
    model.eval()
    total_nll, total_tokens = 0.0, 0
    with torch.no_grad():
        for text in texts:
            ids = tokenizer(text, return_tensors="pt").input_ids.to(device)
            if ids.size(1) < 2:
                continue
            out = model(ids, labels=ids)
            # HF's `labels` loss is mean NLL/token already; recover the sum
            n_tok = ids.size(1) - 1
            total_nll += out.loss.item() * n_tok
            total_tokens += n_tok
    return torch.exp(torch.tensor(total_nll / total_tokens)).item()
```

```python
import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

def measure_kv_cache_bytes(model, tokenizer, seq_len: int, dtype_bytes: int = 4) -> int:
    ids = torch.randint(0, tokenizer.vocab_size, (1, seq_len))
    with torch.no_grad():
        out = model(ids, use_cache=True)
    pkv = out.past_key_values
    total_bytes = 0
    if hasattr(pkv, "layers"):
        # Current transformers: Cache object (e.g. DynamicCache) whose
        # per-layer K/V live on named attributes, not tuple position.
        for layer in pkv.layers:
            for tensor in (layer.keys, layer.values):
                total_bytes += tensor.numel() * tensor.element_size()
    elif hasattr(pkv, "to_legacy_cache"):
        # Intermediate transformers versions: Cache object without
        # `.layers`, but with a legacy-tuple export.
        for key, value in pkv.to_legacy_cache():
            total_bytes += key.numel() * key.element_size()
            total_bytes += value.numel() * value.element_size()
    else:
        # Legacy/older transformers: plain tuple of (key, value) pairs.
        for key, value in pkv:
            total_bytes += key.numel() * key.element_size()
            total_bytes += value.numel() * value.element_size()
    return total_bytes
```

```python
import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

@torch.no_grad()
def draft_propose(draft_model, tokenizer, input_ids, gamma: int):
    ids = input_ids.clone()
    proposed, draft_probs = [], []
    for _ in range(gamma):
        logits = draft_model(ids).logits[0, -1]
        probs = torch.softmax(logits, dim=-1)
        next_id = torch.multinomial(probs, 1)
        proposed.append(next_id.item())
        draft_probs.append(probs[next_id].item())
        ids = torch.cat([ids, next_id.unsqueeze(0)], dim=1)
    return torch.tensor(proposed), draft_probs


@torch.no_grad()
def target_verify(target_model, input_ids, proposed_ids):
    full_ids = torch.cat([input_ids[0], proposed_ids]).unsqueeze(0)
    logits = target_model(full_ids).logits[0]
    start = input_ids.size(1) - 1
    target_dists = []
    for i in range(len(proposed_ids)):
        target_dists.append(torch.softmax(logits[start + i], dim=-1))
    # Bonus distribution for the position right after the last proposed
    # token: this logit is already sitting in `logits` from the single
    # forward pass above, so returning it here costs nothing extra and
    # lets speculative_step skip a second target_model(...) call.
    bonus_probs = torch.softmax(logits[start + len(proposed_ids)], dim=-1)
    return target_dists, bonus_probs


def residual_resample(target_dist, draft_prob_vec_at_this_pos, drafted_token):
    """Sample from max(0, p_target - p_draft) renormalized. We only have
    the draft's scalar probability for the token it proposed, not its full
    distribution, so we approximate: subtract mass only at the proposed
    token's index and renormalize. This is the standard simplification
    used when only the sampled token's draft probability is tracked."""
    residual = target_dist.clone()
    residual[drafted_token] = max(0.0, residual[drafted_token].item() - draft_prob_vec_at_this_pos)
    total = residual.sum()
    if total <= 0:
        return torch.multinomial(target_dist, 1).item()
    residual = residual / total
    return torch.multinomial(residual, 1).item()


def speculative_step(draft_model, target_model, tokenizer, input_ids, gamma: int):
    proposed_ids, draft_probs = draft_propose(draft_model, tokenizer, input_ids, gamma)
    target_dists, bonus_probs = target_verify(target_model, input_ids, proposed_ids)

    accepted = []
    rejected_at = None
    for i in range(gamma):
        p_target = target_dists[i][proposed_ids[i]].item()
        p_draft = draft_probs[i]
        accept_prob = min(1.0, p_target / max(p_draft, 1e-9))
        if torch.rand(1).item() < accept_prob:
            accepted.append(proposed_ids[i].item())
        else:
            corrected = residual_resample(target_dists[i], p_draft, proposed_ids[i].item())
            accepted.append(corrected)
            rejected_at = i
            break

    n_from_draft = rejected_at if rejected_at is not None else gamma

    if rejected_at is None:
        # all gamma accepted: bonus_probs came for free out of
        # target_verify's single forward pass -- reuse it instead of
        # issuing a second target_model(...) call (matches Lesson 4 step 4).
        bonus = torch.multinomial(bonus_probs, 1).item()
        accepted.append(bonus)

    new_ids = torch.cat([input_ids[0], torch.tensor(accepted)]).unsqueeze(0)
    return new_ids, n_from_draft


def speculative_generate(draft_model, target_model, tokenizer, prompt, max_new_tokens, gamma):
    ids = tokenizer(prompt, return_tensors="pt").input_ids
    start_len = ids.size(1)
    total_accepted_from_draft, total_rounds = 0, 0
    while ids.size(1) - start_len < max_new_tokens:
        ids, n_from_draft = speculative_step(draft_model, target_model, tokenizer, ids, gamma)
        total_accepted_from_draft += n_from_draft
        total_rounds += 1
    alpha_hat = total_accepted_from_draft / (total_rounds * gamma)
    return ids, alpha_hat, total_rounds

    _, alpha_hat, rounds = speculative_generate(draft, target, tok, prompt, 60, gamma)
    spec_elapsed = time.perf_counter() - t0

    naive_elapsed = naive_generate_timed(target, tok, prompt, 60)

    measured_speedup = naive_elapsed / spec_elapsed
    predicted_speedup = ((1 - alpha_hat**(gamma+1)) / (1 - alpha_hat)) / (gamma*0.1 + 1) if alpha_hat < 1 else gamma+1

    print(f"measured acceptance rate alpha_hat = {alpha_hat:.3f} over {rounds} rounds")
    print(f"naive:         {naive_elapsed:.2f}s")
    print(f"speculative:   {spec_elapsed:.2f}s")
    print(f"measured speedup:  {measured_speedup:.2f}x")
    print(f"formula-predicted speedup at this alpha: {predicted_speedup:.2f}x")

    cost_per_vcpu_hour = 0.048
    for label, elapsed in [("naive", naive_elapsed), ("speculative", spec_elapsed)]:
        cost_per_1k = (elapsed / 3600) * cost_per_vcpu_hour * 1000
        print(f"{label}: ${cost_per_1k:.4f} / 1K requests")
```

## Three-tier reading

Specific to this module's subject — the arithmetic of making inference cheap, and what that arithmetic doesn't count.

- **Tier 1 — material ground.** Quantization error is measurable, predictable from the bit-width and the tensor's own value distribution, and reproducible — this module had you derive it by hand and check it against a real eval, not take it on faith. Speculative decoding's losslessness is a proven property of its rejection-sampling rule, not a marketing claim; the speedup is bounded by acceptance rate and draft cost, both measurable quantities, not a fixed multiplier a vendor can promise you in the abstract.
- **Tier 2 — what the field suppresses.** "int8 is basically free" and "speculative decoding is a free lunch" are both booster framings that suppress the same fact: every optimization in this module has a *distribution* it works well on and a *distribution* it doesn't, and that second distribution is disproportionately the tail — rare tokens, unusual inputs, out-of-domain queries, exactly the traffic that is hardest to include in the calibration set or held-out eval a team actually runs before shipping. The cost number and the accuracy number both look great on the traffic you tested. The failures concentrate on the traffic you didn't, and nothing in a benchmark table tells you who that traffic belongs to.
- **Tier 3 — sit with this.** Every optimization in this module makes the model cheaper to run by spending its precision unevenly — full precision where the distribution is dense and predictable, degraded precision where it's sparse and surprising. The users whose queries land in the sparse, surprising part of the distribution are, structurally, the users least like whoever built the calibration set. You will ship a quantization level and a speculative-decoding config that passed every eval you ran and hit the cost target you were graded on. When it is wrong, it will be wrong for someone specific, in a way your dashboard reports as "acceptable p99 latency" and "perplexity within budget." What would you have to measure — that this module did not ask you to measure — to find out who that is before they do?

**Lower-severity risk — Lab M02-B's cache introspection may be transformers-version-sensitive.** `measure_kv_cache_bytes` assumes `out.past_key_values` is a tuple of `(key, value)` tuples, one per layer.
