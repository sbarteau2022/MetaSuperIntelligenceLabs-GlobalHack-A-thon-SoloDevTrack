## Lessons

### Lesson 1 — Tokens are the unit the meter runs on

**Teaching text.** A hosted-model API does not bill you for characters, words, or seconds — it bills you for tokens, counted by its own tokenizer, at two different rates: one for the tokens you send (input/prompt) and a higher one for the tokens it generates (output/completion). Both facts surprise learners who have not built the calculator by hand: tokens are not words, and the two directions of the meter do not run at the same speed.

The rate asymmetry is not a pricing gimmick — it is downstream of the same prefill/decode distinction AIE-303-M02 Lesson 3 introduced for the KV cache. Processing a prompt (**prefill**) computes attention over all prompt positions in one parallel pass. Generating a reply (**decode**) computes one token at a time, autoregressively, each step paying a full forward pass that can only start after the previous token exists. Input tokens are cheap to *produce* (from the provider's side, they're a parallel matmul); output tokens are expensive to produce (each one is a serialized round trip through the whole model). The price you're quoted mirrors the compute that made it, not an arbitrary business decision.

For this module's worked examples and labs, use this stated rate (illustrative, dated to this course's writing — provider prices change; before using this for a real budget, replace it with your provider's current published per-token rate, and say in your own writeup that you did):

```
PRICE_PER_MILLION = {"input": 0.15, "output": 0.60}   # USD / 1,000,000 tokens
```

**Worked example.** A summarization request: prompt (the support ticket plus instructions) is 420 tokens, the model's reply is 60 tokens.

```
cost = (420 / 1_000_000) * 0.15 + (60 / 1_000_000) * 0.60
     = 0.000063 + 0.000036
     = 0.000099  ->  $0.000099 / request  ->  $0.099 / 1,000 requests
```

At 50,000 such requests/day: `50,000 * 0.000099 = $4.95/day ≈ $148.50/month`. Notice the output tokens (60, or 12.5% of the total 480 tokens moved) contributed `0.000036 / 0.000099 = 36%` of the cost — output tokens punch above their share of the token count in every request, and that share grows the longer the reply gets relative to the prompt. A system whose replies are twice as long costs meaningfully more than "twice the tokens" would suggest if you'd priced both directions the same.

**Named misconceptions**

- *"A token is roughly a word."* For English prose, a common rule of thumb is ~0.75 words per token, but it is a rule of thumb, not a guarantee — punctuation, whitespace, numbers, code, and non-English text all fragment differently. `"unbelievable"` might be one token or three depending on the tokenizer's vocabulary; `"2024-08-15T09:30:00Z"` is several tokens for what a human reads as one datum. Budget from measured token counts on your own representative text, never from a words-to-tokens conversion factor.
- *"Output tokens cost the same as input tokens, so I can just count total tokens moved."* Wrong by construction of the pricing, and wrong for the mechanical reason above: decode is serialized, prefill is parallel. A request with a short prompt and a long reply can cost more than a request with ten times the prompt and a short reply. Always price the two directions separately.
- *"The token count I get from my local tokenizer is the exact number the provider will bill me."* Different model families use different tokenizers (and providers do not always publish theirs). A local GPT-2-family tokenizer, a `cl100k`-style tokenizer, and a provider's proprietary tokenizer will each produce a *different* count for the same string — usually close, not identical. Treat any locally-computed token count for a third-party API as an estimate unless you are counting with that provider's own tokenizer or counting endpoint.

### Lesson 2 — Amortized hardware cost: the $/1K-requests number M02 already computed, generalized

**Teaching text.** AIE-303-M02's labs ended every measurement with a `$/1K requests` line: `(latency_seconds / 3600) * cost_per_vcpu_hour * 1000`. That formula has two assumptions baked silently into it — **concurrency = 1** (the box serves exactly one request at a time) and **utilization = 1.0** (the box is never idle, every paid second serves a request). Neither holds in production, and both matter more to your final cost than the quantization step M02 spent a whole module on.

The generalized formula:

```
requests_per_hour = concurrency * (3600 / latency_seconds)
cost_per_request  = cost_per_hour / (requests_per_hour * utilization)
```

`concurrency` is how many requests the box can genuinely have in flight at once — bounded by the KV-cache memory budget from AIE-303-M02 Lesson 3, among other things. `utilization` is the fraction of paid box-hours that actually carry traffic; a box billed 24/7 that only sees daytime load might run at 0.3–0.4 utilization, and every idle hour is still on the invoice. Both terms multiply the effective throughput, and — critically — `cost_per_request` is inversely proportional to *both*, so a change in either one moves the bill by exactly the same leverage as a change in raw latency.

**Worked example.** Using `cost_per_vcpu_hour = $0.048` (M02's stated rate) and an int8-quantized `distilgpt2` measured at `latency = 0.27s/request` (illustrative measured number for this worked example — substitute your own AIE-303-M02 Lab A run):

| Assumption | effective requests/hour | cost/request | $/1K requests | vs. step 1 |
|---|---|---|---|---|
| 1. concurrency=1, utilization=1.0 (M02's implicit assumption) | 13,333 | $0.0000036 | $0.0036 | baseline |
| 2. + realistic utilization=0.35 (bursty daytime traffic) | 4,667 | $0.0000103 | $0.0103 | 2.86× worse |
| 3. + concurrency=6 (KV-cache budget allows 6 in-flight, from M02 L3) | 28,000 | $0.0000017 | $0.0017 | 2.1× *better* than baseline |

Step 2 alone makes the box 2.86× more expensive per request than M02's number implied — exactly `1/0.35`. Step 3's concurrency then more than pays that back: `concurrency × utilization = 6 × 0.35 = 2.1`, and cost divides by exactly that combined factor relative to baseline (`0.0036 / 2.1 = 0.0017`, matching the table). The lesson is not "quantization didn't matter" — it's that **concurrency × utilization is a bigger lever than any single quantization step**, and a cost model that reports only the M02-style single-request number has quietly assumed away the two biggest terms.

**Named misconceptions**

- *"The `$/1K requests` number M02's labs printed is production-ready."* It is a valid, honest number for what it measured — single-stream latency — but it assumes concurrency=1 and utilization=1.0, both optimistic. Report it as "per-request compute cost at full utilization," not "cost per request," unless you've also modeled the other two terms.
- *"Multiplying single-request latency by an assumed concurrency count tells you real concurrent throughput."* It gives you an analytic *ceiling*. Real concurrent serving has contention — for CPU inference, competing threads slow each other down; for GPU serving, batching changes the compute shape entirely. This lesson's concurrency term is a planning estimate; measuring it for real is AIE-303-M01's load-testing harness, not this module's arithmetic.
- *"Self-hosting is always cheaper than an API because there's no per-token markup."* A self-hosted box has a **fixed** cost that runs whether or not it serves a single request; an API has **zero** fixed cost and a purely marginal per-request price. Which is cheaper depends on volume — that comparison is Lesson 4.

### Lesson 3 — A request is not one line item: composing the full $/request

**Teaching text.** The AIE-302 system a learner is costing here is not a single model call. A typical RAG-or-agent request touches an embedding call (to encode the query for retrieval), a vector lookup (near-zero marginal cost — it's a database read, not a model call), and one or more generation calls — often more than one, because an agent loop may reason, call a tool, and re-check its own answer before returning. The defensible $/request number is the **sum across every stage that actually runs**, not just the final generation call, and — this is the trap — it is not a fixed number across requests, because the number of generation calls and the size of the accumulated context both vary per request.

The accumulation trap is specific and worth deriving once: in a typical agent loop that resends the full running conversation as context on every step (rather than a smarter cache), each new iteration's **input** tokens include every prior iteration's input *and* output. Cost per iteration is not constant — it grows with iteration count, because the context it's billed on grows with iteration count. A learner who estimates total loop cost as `(cost of one call) × (number of iterations)` will underestimate, because that estimate prices every call at the *first* iteration's (smallest) context size.

**Worked example.** A RAG request: 5 retrieved chunks (~200 tokens each) plus a 30-token question, 1,030 input tokens, answered in 150 output tokens, single-shot (no agent loop):

```
cost = (1,030/1e6)*0.15 + (150/1e6)*0.60 = 0.0001545 + 0.00009 = $0.0002445 / request
```

Now the same system running as a 4-step agent loop (reason, call a tool, re-check, answer) with a fixed 1,000-token base context and per-step output tokens `[80, 80, 80, 150]`, where each step's input is the base context plus every token produced so far:

| Iteration | Input tokens | Output tokens | Cost |
|---|---|---|---|
| 1 | 1,000 | 80 | $0.000198 |
| 2 | 1,080 | 80 | $0.000210 |
| 3 | 1,160 | 80 | $0.000222 |
| 4 | 1,240 | 150 | $0.000276 |
| **Total** | **4,480** | **390** | **$0.000906** |

The naive linear estimate — iteration 1's cost times 4 — is `0.000198 × 4 = $0.000792`. The actual accumulated cost, $0.000906, is **14.4% higher**. That gap is not measurement noise; it is the direct, arithmetic consequence of resending a growing context on every step, and it is the same accumulation that made AIE-303-M02's KV cache grow linearly with sequence length — here it grows your bill instead of your memory footprint.

**Named misconceptions**

- *"Each call in an agent loop costs about the same, so multiply by the loop count."* Shown false above by 14.4pp on a 4-step loop; the gap widens with more steps or a larger base context, because it's driven by re-sending accumulated history, not by anything about the loop's logic.
- *"Retrieval is free — it's just a database lookup."* The *lookup* is close to free. The chunks it returns are not: they become generation-stage **input tokens**, and Lesson 1 already showed input tokens are not zero-priced. Retrieval's real cost shows up on the generation line, disguised as "context," which is exactly why a cost model that only itemizes "the LLM call" undercounts a RAG system's retrieval design decisions (how many chunks, how long each one is).
- *"The $/request number is a single figure I can report."* It's a distribution — driven by variable loop length, variable chunk count, variable output length. A defensible budget states an *average* and states what drives the *tail*, which is exactly where Lesson 4 goes next.

### Lesson 4 — Defending the budget: averages don't survive a skeptical reader

**Teaching text.** A cost model presented as a single average number invites exactly one question from anyone with a finance background: "what's the worst case, and how often does it happen?" This module treats that question as required, not optional, because the same accumulation effect from Lesson 3 means your worst case is not a small perturbation of your average — it can be several times larger, and if it happens on even a modest fraction of traffic, it moves the total bill by more than the average alone would predict.

**Blending average and worst case.** Using Lesson 3's two numbers — average-case single-shot request at $0.0002445, worst-case 4-step-loop request at $0.000906 — at 100,000 requests/month with a stated 5% worst-case rate:

```
blended_cost = 100,000 * (0.95 * 0.0002445 + 0.05 * 0.000906)
             = 100,000 * (0.00023228 + 0.0000453)
             = 100,000 * 0.00027758
             = $27.76/month
```

versus an average-only estimate of `100,000 * 0.0002445 = $24.45/month` — the average-only budget **underestimates the real bill by 13.5%**. That gap is the cost of not modeling the tail; it is not a rounding error, and it grows with the worst-case rate and the size of the accumulation gap.

**Self-hosted vs. API: the breakeven volume.** Self-hosting has a fixed monthly cost that runs whether or not traffic arrives; an API has zero fixed cost and a pure marginal price. Using one always-on vCPU box at M02's `$0.048/vCPU-hour` (`0.048 × 24 × 30 = $34.56/month` fixed) against the API price of Lesson 3's RAG request ($0.0002445):

```
breakeven_requests_per_month = fixed_monthly_hardware_cost / provider_cost_per_request
                              = 34.56 / 0.0002445
                              ≈ 141,350 requests/month
```

Below ~141,350 requests/month, the API is cheaper — you are paying for idle box-hours the API never bills you for. Above it, the fixed box wins because its marginal cost per additional request is close to zero. This is why "self-hosting is cheaper" and "the API is cheaper" are both true statements, at different points on the same volume axis, and why a defensible budget states its assumed volume, not just its per-request number.

**Named misconceptions**

- *"The average $/request is what I defend against the SLO."* A skeptical reader accepts an average paired with a stated worst case and a stated worst-case rate — not an average alone. The blended-cost calculation above is the minimum bar; report it, not just the average.
- *"A $/request under budget means ship it."* Cost and quality are separate gates. AIE-204's eval harness is the quality gate; this module is the cost gate. A quantization level or a shortened context window can hit a cost target by making the system worse in exactly the way an eval would catch — the two gates exist so that a cheaper system is never a euphemism for a worse one that got quietly relaxed to hit a number.
- *"Fixed costs don't matter below capacity — I'm not paying for what I don't use."* The opposite is true: a self-hosted box's fixed cost is what you pay whether or not you use it, which is precisely why utilization was Lesson 2's dominant lever and why the breakeven volume above is a real threshold, not a formality.

from transformers import AutoTokenizer

PRICE_PER_MILLION = {"input": 0.15, "output": 0.60}  # USD / 1,000,000 tokens


def count_tokens(tokenizer, text: str) -> int:
    return len(tokenizer.encode(text))


def request_cost(n_input_tokens: int, n_output_tokens: int, price_per_million: dict) -> float:
    return (n_input_tokens / 1e6) * price_per_million["input"] + \
           (n_output_tokens / 1e6) * price_per_million["output"]


def agent_loop_cost(base_context_tokens: int, turn_output_tokens: list[int],
                     price_per_million: dict) -> dict:
    total_input, total_output, breakdown = 0, 0, []
    running_context = base_context_tokens
    for out_tok in turn_output_tokens:
        input_tok = running_context
        cost = request_cost(input_tok, out_tok, price_per_million)
        breakdown.append({"input_tokens": input_tok, "output_tokens": out_tok, "cost": cost})
        total_input += input_tok
        total_output += out_tok
        running_context += out_tok
    total_cost = sum(b["cost"] for b in breakdown)
    return {
        "total_input_tokens": total_input,
        "total_output_tokens": total_output,
        "total_cost": total_cost,
        "breakdown": breakdown,
    }

import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer


def measure_latency(model, tokenizer, prompt: str, max_new_tokens: int, n_runs: int = 5) -> float:
    """Average wall-clock seconds per model.generate() call, after one
    untimed warmup call."""

def system_request_cost(retrieval_input_tokens: int, retrieval_price_per_million: dict,
                         generation_input_tokens: int, generation_output_tokens: int,
                         generation_price_per_million: dict) -> dict:
    retrieval_cost = request_cost(retrieval_input_tokens, 0, retrieval_price_per_million)
    generation_cost = request_cost(generation_input_tokens, generation_output_tokens,
                                    generation_price_per_million)
    return {
        "retrieval_cost": retrieval_cost,
        "generation_cost": generation_cost,
        "total_cost": retrieval_cost + generation_cost,
    }


def worst_case_vs_average_cost(base_context_tokens: int, avg_iterations: int,
                                max_iterations: int, per_iteration_output_tokens: int,
                                price_per_million: dict) -> dict:
    avg_result = agent_loop_cost(
        base_context_tokens, [per_iteration_output_tokens] * avg_iterations, price_per_million)
    worst_result = agent_loop_cost(
        base_context_tokens, [per_iteration_output_tokens] * max_iterations, price_per_million)
    return {"average_cost": avg_result["total_cost"], "worst_case_cost": worst_result["total_cost"]}


def blended_monthly_cost(average_cost: float, worst_case_cost: float,
                          monthly_requests: int, worst_case_rate: float) -> float:
    return monthly_requests * (
        worst_case_rate * worst_case_cost + (1 - worst_case_rate) * average_cost
    )


def defend_budget(actual_cost_per_request: float, target_cost_per_request: float) -> dict:
    passes = actual_cost_per_request <= target_cost_per_request
    headroom_pct = 100 * (target_cost_per_request - actual_cost_per_request) / target_cost_per_request
    return {"passes": passes, "headroom_pct": headroom_pct}

## Three-tier reading

Specific to this module's subject — the arithmetic of what a request costs, and what that arithmetic doesn't count.

- **Tier 1 — material ground.** A request's cost is measurable and reproducible: token counts from a stated tokenizer, prices from a stated (dated) rate card, hardware cost from a stated cost-per-hour and measured latency, all of it traceable and auditable the way this module's labs required. Nothing about the arithmetic is in dispute — a skeptical reader can check every line.
- **Tier 2 — what the field suppresses.** A public "$0.002 per query!" headline number is almost always the average-case, full-utilization, single-shot number — exactly the number Lesson 2 and Lesson 4 showed is the *least* representative one a production system actually pays. It suppresses utilization (idle box-hours nobody advertises), suppresses the accumulation effect on multi-step agent loops, and suppresses retries — a request that fails an eval gate and gets regenerated is a request that got billed twice, and that cost is invisible in any number computed before the eval harness existed. The number that gets published is the number that makes the best case; the number a team actually pays is the blended one, and the gap between them is not usually disclosed, because there is no obligation to disclose it and every incentive not to.
- **Tier 3 — sit with this.** The cheapest way to hit a $/request target is not to make every request cheaper equally — it's to make the *expensive* requests cheaper, and the expensive requests are disproportionately the ones with long contexts, long agent loops, and unusual retrieval patterns: the complex, atypical, hard-to-serve queries. Those are frequently the queries from the users the system already serves least well — the ones whose questions don't fit the common case, whose context doesn't compress cleanly, whose intent takes the agent more steps to resolve. A budget defended against an average user can be hit, cleanly and honestly, by quietly shrinking the system's effort on exactly the requests that already needed more of it — and every number in this module's rubric would still look green while that happens, because none of them measure who the savings came from. What would you have to add to this module's cost model — a column this module never asked you to build — to find out whether your budget was balanced on the backs of your hardest-to-serve users, before your users find out for you?
